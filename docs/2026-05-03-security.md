# Security-Konzept (Stand 2026-05-03)

Ziel: Selbst wenn ein Angreifer das Telefon physisch in die Hand bekommt oder ein Backup extrahiert, sollen die Ausgaben des Nutzers nicht lesbar sein.

## Threat Model (was wir abwehren)

1. **Verlorenes / gestohlenes Gerät** – Angreifer hat Zugriff auf das Dateisystem.
2. **Lokales Backup** – z. B. unverschlüsseltes Android-Backup auf den PC.
3. **Andere Apps auf dem Gerät** – die nicht direkt auf unsere Daten zugreifen können sollen.
4. **Schultergucker / Mitbenutzer** – die App soll sich automatisch sperren.

Was wir **nicht** abwehren (außerhalb des Scopes):
- Vollständig kompromittiertes / gerootetes Gerät mit aktivem Malware-Stack.
- Hardware-Angriffe auf den Secure-Element-Chip.
- Schadhafte Builds aus inoffiziellen Quellen.

## Bausteine

### Passwort-Hashing: Argon2id

- Algorithmus: **Argon2id** (RFC 9106).
- Parameter (in `app_constants.dart`): `t=3 iterations`, `m=64 MB`, `p=4 parallelism`, `hashLen=32`, `saltLen=16`.
- Salt wird pro Nutzer **kryptografisch zufällig** erzeugt.
- Es wird **nur der Hash** gespeichert, nie das Passwort.
- Login: User-Eingabe → Argon2id mit gespeichertem Salt → Vergleich in **konstanter Zeit** (`crypto.constant-time-equals`-Äquivalent), um Timing-Angriffe zu vermeiden.

### Sicherer Speicher: flutter_secure_storage

- Nutzt **Android Keystore** (HW-gestützt ab Android 6) und **iOS Keychain**.
- Hier landen ausschließlich:
  - Argon2id-Hash + Salt
  - Datenbank-Passphrase
  - Biometrie-Flag
- Niemals: Klartext-Passwort, Bon-Daten, Beträge.

### Datenbank: SQLCipher

- `sqflite_sqlcipher`, AES-256 Page-Level-Encryption.
- DB-Passphrase wird beim ersten Start mit `Random.secure()` (32 Byte) generiert und im Secure Storage abgelegt.
- Ohne diese Passphrase ist die DB-Datei unlesbar – auch in einem Backup.

### Biometrie: local_auth

- Optionale, **bequeme** Zweitmethode neben dem Passwort.
- Biometrie schaltet **nicht** das Passwort ab; sie ist nur ein „Schlüssel zum bereits abgelegten Hash".
- Bei drei Fehlversuchen fällt die App auf das Passwort zurück.

### Auto-Logout

- Standard: nach **5 Minuten Inaktivität**.
- Wird über einen Inactivity-Timer im Wurzel-Widget realisiert.
- Beim Backgrounding (App-Switcher) wird die UI mit `SecureFlag`/`Blur` überdeckt, damit im Task-Switcher keine Beträge sichtbar sind.

### Login-Bremse

- Nach **5 Fehlversuchen**: 1 Minute Cooldown.
- Verhindert simples Brute-Force, ohne den Nutzer bei einem Tippfehler zu blockieren.

## Coding-Praktiken

- **Keine Secrets im Code.** Alle Schlüssel-Namen sind Konstanten, die Werte werden zur Laufzeit erzeugt.
- **Kein Logging sensibler Daten.** `logger` wird nur für Flow-Events genutzt, nie mit Beträgen oder Passwort-Eingaben.
- **Strict Lint-Regeln** (`analysis_options.yaml`): `avoid_dynamic_calls`, `only_throw_errors`, `strict-casts`.
- **Pinned Dependencies** im `pubspec.yaml` – kein offenes `any`, damit kein unbemerktes Major-Update reinrutscht.
- **`flutter test --coverage`** als Pflicht-Schritt vor Releases (Schritt 9).
- **Release-Build mit Obfuscation:**
  ```bash
  flutter build apk --release --obfuscate --split-debug-info=build/symbols
  ```

## Was passiert bei „Passwort vergessen"?

Bewusste Designentscheidung: **kein Passwort-Reset**, weil das den Schutz durchbrechen würde. Stattdessen:

- „Account zurücksetzen" löscht die DB und alle Secrets, der Nutzer fängt mit leeren Daten neu an.
- Vor dem Reset eine sehr deutliche Warnung mit Bestätigungs-Eingabe.

## Tests, die diese Annahmen absichern

- **Unit:** Argon2id-Wrapper liefert für gleiches Passwort+Salt denselben Hash; für unterschiedliche Salts unterschiedliche Hashes; Verify schlägt bei falschem Passwort fehl.
- **Unit:** Auto-Logout-Logik feuert nach genau N Sekunden Inaktivität.
- **Integration:** App-Restart nach Logout zeigt Login-Screen, nicht Home.
- **Integration:** Falsches Passwort 5× → Cooldown aktiv.
